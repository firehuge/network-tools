How to use FlowMapper

Each topic has two parts: In plain words for anyone, and Technical detail for engineers. Everything runs in this browser; nothing is uploaded.

1. Start here: trace a flow in five steps
  1. Load the config. Click Load config XML (or drop files). Use a Panorama export, firewall backups, or both together.
  2. Type the flow. Source, destination, protocol and port, for example 10.20.1.50 to 10.10.1.20, tcp, 443.
  3. Click Trace. The tool walks the path firewall by firewall: zones, routes, NAT and the rule that matches at each hop.
  4. Read the coloured box at the top. Green: Complete. Yellow: Suggested (some hop is a well-founded guess). Red: Incomplete or Needs your choice.
  5. Act on it. The box says what to confirm, or which firewall to pick. The Changes list says which rules or routes to add.
2. What the path labels mean

In plain words: the label tells you how much to trust the path.

  • Complete: every hop comes straight from the configs, your links or the public-space map.
  • Complete (pasted route table): as above, and at least one hop used a route you pasted from a real firewall.
  • Suggested (BGP-inferred): a hop relies on a BGP route the tool worked out from the BGP settings. Probably right, not proven. Paste that firewall's route table to make it certain.
  • Suggested: another kind of educated guess (a router not in the export, a default route to the unknown).
  • Needs your choice: the same address is configured on more than one firewall, so the tool will not guess. Pick one (see topic 5).
  • Incomplete: the trace stopped. The box says where, why and how to fix it.

Technical detail: each hop lists its assumptions with a confirm step. Pins you make are shown as "pinned by your choice" and do not lower the label.

3. BGP: what the tool can and cannot know offline

In plain words: a firewall config shows who talks BGP with whom and what each side is allowed to announce. It does not show what was actually learned. So the tool plays BGP forward: "firewall A announces network X to its neighbour B, so B can reach X through A". Those hops are labelled Suggested (BGP-inferred) and each one explains why.

Technical detail. Read from Panorama templates / template stacks and from local backups:

  • Legacy virtual routers (network/virtual-router/.../protocol/bgp): local AS, router ID, peer groups (iBGP / eBGP), peers, redistribution rules and redistribution profiles, import / export policy rules (used-by, address-prefix, exact), aggregation (summary or not), conditional advertisement (non-exist and advertise filters).
  • Advanced routing, PAN-OS 10.2+ (network/logical-router/.../vrf/.../bgp with network/routing-profile): peer groups and peers (with per-peer inherit no overrides), redistribution profiles (static / connected / OSPF / RIP, with route maps), advertise-network network statements, aggregate routes (summary-only), BGP filtering profiles (inbound / outbound prefix lists, distribute lists and route maps) and conditional advertisement (exist / non-exist maps).
  • Legacy import / export rules are read top to bottom per peer group (first match wins). Once any rule applies to a peer group, a route that matches none of them is not exchanged. This is how PAN-OS behaves, so a list with only a deny rule blocks everything unless it ends with an allow-everything rule.
  • Peers are matched to loaded firewalls by address. A peer that is not a loaded firewall (MPLS PE, ISP) becomes a provider "fabric": firewalls peering into the same AS learn each other's announcements.
  • Conditional advertisement is decided against what the config says is in the table; at runtime it can differ, so those routes have low confidence and say so.
  • When a route is missing, the change list says what BGP setting withheld it (prefix list, export rule, conditional advertisement).
  • Not modelled: AS-path / community matching, MED, local preference and other best-path tie-breaks, route reflector clusters, BFD / timers, IPv6, OSPF on advanced routing. Paste the route table when these matter.
4. Pasting a real route table (makes BGP hops certain)

In plain words: run one command on the firewall, copy the output, paste it under Route tables on the Trace tab, pick which firewall it came from, and click Apply. That firewall's BGP hops then use real routes instead of guesses.

Technical detail: accepted inputs are show routing route (legacy), show advanced-routing route (advanced routing), the XML API response to <show><routing><route/></routing></show>, or a CSV router,destination,nexthop,interface,protocol[,distance,metric]. Only active IPv4 routes are used. Connected / host routes are skipped (the config has them); static routes are added only if the config lacks them. A router with a pasted table gets no inferred routes. Tables live in memory only; reload the page and they are gone.

5. Same IP on several firewalls (cloned builds, overlapping space)

In plain words: sometimes two data centers are built from one template, so both firewalls have exactly the same addresses. Or two sites reuse the same private range. The tool never guesses which one traffic reaches. It shows Needs your choice with one row per candidate firewall (hostname, serial, template stack, site, and why it fits). Click Use for this trace to decide for this trace only, or Save as link so every trace from that interface goes there.

Technical detail:

  • HA pairs are merged first. Firewalls are paired as HA only when their HA config names each other, or (when no HA config is loaded) they share the same template stack, nearly identical interface addresses, and the same site in their hostnames. Different stacks never pair; different sites (for example dc1 vs dc2) never pair without HA config.
  • The Overlapping address space callout under the loaded files lists every address configured on more than one firewall, overlapping subnets, and look-alike firewalls with the reason they were kept apart.
  • Decision points: a next hop owned by several firewalls; a source or destination inside a subnet whose gateway address is the same on several firewalls. One subnet shared by several firewalls with different addresses is a normal shared segment and is not flagged.
  • Pins: Use for this trace sets the branch choice (next hop) or the source / destination firewall. Save as link adds a link (from firewall + egress interface to the chosen firewall), stored in this browser with your other links.
  • A BGP peer address owned by several firewalls is only matched when exactly one is at the same site; otherwise it is left out of inference and counted as an ambiguous peer.
6. Links, public-space map and hostnames

In plain words: when routers between firewalls are not in the configs, tell the tool where traffic goes with a link. The public-space map says which circuit each public range arrives on. Device hostnames names firewalls that only show a serial.

Technical detail: links have the highest weight in path finding and make hops explicit (Complete). All three are stored in this browser's localStorage and can be exported as JSON.

7. Production only: leave DR out

In plain words: many networks have a production site and a disaster-recovery (DR) site built almost alike. If you only care about production, switch the Scope bar (above the tabs) to Production only. DR, Lab and Test firewalls then stay out of traces, next-hop choices, pickers, alternate paths, diagrams, batch runs and plans. All sites brings everything back. A chip always tells you what is hidden, for example Scope: Production only, 12 DR firewalls hidden.

  • How it knows: it looks for plain words such as prod, dr, backup, lab or test in a firewall's hostname, template-stack and device-group names. Each guess shows its reason under Site roles. If there is no clue, the firewall stays Other and is kept.
  • You decide: under Site roles, add matching rules (for example: template stack contains a word you type → DR). First match wins. You can still set one site or one firewall by hand. Export the settings as a JSON file to reuse them.
  • If DR is needed to finish a path: the trace says so and offers Show all sites, instead of failing silently.
  • DR copy advice: when a plan adds rules on production firewalls, the tool lists DR firewalls that probably need the same rule (same stack pattern, device group, hostname pattern and zones). It never traces DR for this; it is advice. If a DR firewall shares the device group, a rule pushed there already reaches it.
  • Panorama HA: Panorama itself can be an HA pair with one peer at each site. Roles are for firewalls only. The Panorama pair has its own Role and Active/Passive on the Environment tab (Panorama view) and never changes which firewalls are in scope. Loading either peer's export gives the same result.

Technical detail: evidence weights are hostname 3, template stack 2, device group 2; weak words (primary, secondary, standby) only count from stack and device-group names. Authority order: your firewall setting, your site setting, the firewall's own clue, the site's majority clue, then Other. HA secondaries follow their primary. HA pairs are decided on the full list first, so hiding a firewall never creates a pair. Inferred BGP/OSPF routes are recomputed for the scoped list, so a route that only a DR peer would advertise is not used.

FAQ: How do I look at production only? Click Production only in the Scope bar. If nothing is hidden, open Site roles and add a rule (template stack or hostname contains the word that marks your backup site) set to DR, or mark the site by hand.

FAQ: Why did the routing/rules conflict count jump when I chose Production only? Usually because the routed path went through a DR firewall that is now hidden. The Validate summary splits conflicts that only appear because the scope hid the routed next hop (or the address's owner) from conflicts that also exist with All sites. Those first ones are not, by themselves, stale rules; switch to All sites to see the routed path.

FAQ: My Panorama is HA across production and DR, so why do I see both sites and how does Production only work? A Panorama export lists every firewall that Panorama manages, production and DR alike, and both Panorama peers hold the same list, so you see both sites whichever peer you exported from. Production only does not look at Panorama at all: it hides the firewalls whose site is marked DR (or Lab or Test). The two Panoramas are not firewalls, so they are never hidden and never change the scope; they have their own Role and Active/Passive on the Environment tab.

8. Before you push a change

FlowMapper reads configuration only. Always confirm on the firewall with test security-policy-match, test nat-policy-match and test routing fib-lookup (legacy) or test advanced-routing fib-lookup (advanced routing).

Site roles — matching rules, and which firewalls are Production, DR, Lab or Test
Firewall change request (FCR) — paste a flow or a CSV, then get every hop, one change plan, a pre-push checklist and traffic-log filters

Paste one flow (10.1.1.10 -> 10.2.2.20 tcp/443), several lines, or a CSV with columns such as source, destination, protocol, port, application, ticket. The tool traces every vsys the packet crosses so you can write one change set instead of pushing a rule, finding the next deny, and pushing again. Nothing is uploaded.

Links between firewalls - tell the tool which firewall is behind a router/MPLS hop that is not in the config
Saved in this browser (localStorage), keyed by firewall name.
Route tables (actual learned routes) - paste what a firewall really has, so BGP/OSPF hops stop being guesses

The config says who peers with whom, not what was learned. Paste the output of show routing route (legacy virtual routers), show advanced-routing route (advanced routing / logical routers), the XML API answer, or a CSV of router,destination,nexthop,interface,protocol (for example from a tech-support file). Pasted routes win over inferred ones: that router gets no inferred routes, and hops that use a pasted route count as explicit. Kept in memory only; nothing is saved or uploaded.

Device hostnames - for firewalls shown only by serial (Panorama exports often leave out managed-device hostnames)

Paste serial,hostname lines, or a CSV export of Panorama > Managed Devices (columns named like Device Name and Serial Number). Hostnames from the config always win; these fill the gaps. Saved in this browser.

Public-space map - which circuit / upstream router each public prefix arrives on, and where it lands

Public space is often routed by provider or upstream routers that are not in the firewall configs. For each public prefix, say which circuit it arrives on and which firewall (and interface or zone) it lands on. Traces of inbound flows whose source or destination is in a mapped prefix enter there (longest prefix wins; HA peers count as one firewall) and flag disagreements with routing.

Saved in this browser (localStorage), keyed by firewall name.
Validate with existing rules - replay the allow rules in this config and check the tool finds a path through each rule's own firewall and zones

Inference details - inferred routers and shared subnets (sanity-check what the tool assumed)

Sites are inferred: HA groups, firewalls sharing a LAN subnet (not point-to-point, tunnel or WAN-core subnets), the same hostname site token (firewall words and unit numbers removed), or a device group used by exactly two firewalls. Hover a site for the reason. Click a firewall to expand its vsys, zones and interfaces; double-click for its detail diagram. By vsys groups every vsys on a firewall (HA pairs folded), pulls the vsys of the last trace out, collapses the rest into an “other vsys” pool, and draws an unknown-network cloud for next hops no loaded firewall owns. Export draw.io from any mode.


  
PAN-OS FlowMapper works offline. It reads the configuration only; it cannot see dynamic routes, FQDN resolution, User-ID, or App-ID at runtime. Always confirm with test security-policy-match, test nat-policy-match and test routing fib-lookup on the firewall.
